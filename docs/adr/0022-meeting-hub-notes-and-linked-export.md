# ADR 0022: Meeting Hub, Personal Notes and a Linked Export

**Status**: Proposed (Windows fork)
**Date**: 2026-11-02
**Builds on**: [ADR 0019: Markdown Export Contract and Export Folder](0019-markdown-export-contract-and-export-folder.md), [ADR 0021: Optional Summary Server](0021-optional-summary-server-on-the-local-network.md)
**Context**: Mynota records, transcribes and summarizes. The user wants it to be the one place that holds everything about a meeting, a web conference or a technical talk played on the computer (all three are captured the same way, as system audio): the transcript, the summaries (a local model, a server, or text pasted from an outside assistant), the user's own notes taken while listening, and a Markdown export in a note vault such as Obsidian. Four gaps stand in the way:

- The "Notes" tab is a summary template, not a place for the user's remarks.
- The export file is named after the date and title, so renaming a meeting leaves the old file behind (an open risk of ADR 0019).
- The audio is the heavy part of a meeting, and there is no way to free it while keeping the rest.
- A summary can only be generated by the app, not pasted.

## Decision

The meeting stays the unit. The exported file is a **view of it that remains linked**.

### 1. Stable link between a meeting and its file

- The meeting stores the **relative path of its exported file**. The front matter gains `mynota_id` (the meeting id) next to the existing fields.
- A re-export writes to the linked file even if the title changed, and renames the file only when the user asks to. No second file is created.
- If the linked file is missing, the export recreates it at the default name and the interface says so. Nothing is deleted without being asked.

### 2. Relinking in the interface

When the link is broken (file moved, renamed or removed in the vault), the meeting detail shows the export state (linked, missing, not exported) and offers:

- **Relink to a file…**: pick a Markdown file in the export folder; the meeting adopts it.
- **Recreate the export**: write a fresh file and link it.
- **Unlink**: forget the file without touching it.

On start and on demand, the app also scans the export folder (sub-folders included) for files whose front matter carries a known `mynota_id`, and relinks them by itself. Moving a file inside the vault therefore needs no action.

### 3. The user's own notes

- Each meeting gets a free Markdown **"My notes"** text, stored with the meeting, in its own tab (the summary template tab keeps its role and is renamed in the interface to avoid the clash).
- **While recording or listening**, a note box adds a line prefixed with the elapsed time (`[00:12:40] check this point`), so a remark lands at the right moment of the talk. The box takes dictation from any tool that types into a field.
- Notes are plain text on disk, exported as a section, and never rewritten by a summary run.

### 4. Pasted summaries

A meeting can hold a summary pasted by the user under a label of their choice (for example the name of the outside assistant). It is stored like any summary, marked as external, and never regenerated. Generated summaries keep their template and language.

### 5. Export layout and what the app may overwrite

Order: front matter, transcript, summaries, notes. The transcript stays first, as in ADR 0019, so existing consumers of the file keep working. Front matter additions are `mynota_id` and `status` (`to-summarize`, `summarized`, `archived`).

Each generated block sits between HTML comment markers (`<!-- mynota:begin transcript -->` … `<!-- mynota:end transcript -->`, same for `summary` and `notes`). A re-export **rewrites only the marked blocks**; any text the user adds outside them in the vault is preserved. Without markers (a file written before this change, or markers removed), the export refuses to overwrite and asks the user to relink or recreate.

### 6. Audio purge

- **Purge audio** removes the audio files of a meeting and keeps the transcript, summaries, notes and export. It is allowed only when a transcript exists, asks for confirmation, and is available per meeting and in bulk ("older than N days", with a count shown before confirming).
- A purged meeting cannot be re-transcribed or have its speakers re-detected; the interface says so.
- The export never contains audio.

### 7. Archive

Archiving already exists in the backend. Archived meetings leave the main list, stay searchable, can be shown again through a filter, and their export gets `status: archived` instead of disappearing.

## Out of scope

- Fetching video or audio from a web address: a talk is listened to on the computer and captured as system audio, like a meeting.
- Two-way sync of the transcript or summaries from the vault back into the app. Only the link and the preserved free text are handled.
- Other export targets (Notion, PDF, subtitles): upstream's roadmap.

## Consequences

- `meeting.json` gains optional fields (`export_path`, notes), all `#[serde(default)]`, so older meetings load unchanged.
- The markers add a few comment lines to the file; plain readers ignore them.
- The export code changes from "write a whole file" to "merge marked blocks", which needs careful tests (missing markers, edited text outside blocks, renamed title).
- The UI gains one tab, one export-state strip and one purge action; translations follow ADR 0020 (English and French).

## Open Risks

- A file edited inside a marked block is overwritten on the next export. The markers say "generated" to make this visible.
- Purging audio is irreversible; the confirmation and the bulk count are the only safeguard.
- The scan by `mynota_id` reads front matter of every Markdown file in the export folder; a very large vault may need a cap or a dedicated sub-folder (to measure).
